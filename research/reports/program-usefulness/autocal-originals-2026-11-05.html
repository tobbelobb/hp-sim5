What worked

The Program did better science than its final usefulness suggests.

Several controls, provenance checks and failure preserves are genuinely good. They reduce the chance of adopting a false improvement. They do not remove the human’s remaining work.

✓Strengths

  • Prompt refresh had substance. The manager checked prior reports and rewrote the prompt to retire settled profiling, blind thinning and unconditional solver/default proposals.
  • Experimental discipline was strong. It declared development and evaluation worlds, froze the candidate before held-out scoring, and kept truth out of selection.
  • The intervention was verified. Stock guide-friction material did not affect the capstan solve; the worker used isolated ECS injection and checked native readbacks and hashes.
  • The negative result is useful. The probe shows torque can coexist with tens of millimetres of local slack, which is a concrete model-boundary concern rather than a vague tool complaint.
  • Independent review did its job. The reviewer recalculated saved geometry, checked hashes and source, and returned supported / keep / report_only with explicit limits.
  • Budgeting and durability recovered well. The worker stayed inside its numerical budget, and 407 original files were recovered with verified hashes after the workspace access failure.

×Weaknesses

  • No delivered change. The branch adds a prompt revision and 63.4 MiB of research evidence, but no source, test or integration record.
  • The first assignment was a screen, not a delivery mission. “Test robustness” made a report-only ending predictable; the implementation-oriented assignment was only commissioned at the end.
  • Most visible work reconfirmed known ground. Two accepted nominal calibrations and a matched control establish that defaults still work; the genuinely new signal is the guide-transport concern.
  • Operational failures were mostly hidden in the notebook. The concise README mentions command access but not the recorder timeout, SIGTERM, recorder-readiness failure, probe crashes or review timeout.
  • Review and recovery dominated the tail. Roughly 80 minutes passed between worker exit and admission, largely because of a timeout and workspace outage.
  • One status is overstated. The readable entry point says the second worker was “dispatched”; the controller says the assignment is only ready, with no attempt record.

Recommendations

Change the contract before adding more orchestration.

The highest-value fixes are delivery authority, prompt triage, checkpointing and a real worker-context canary. Longer time is useful only after those are in place.

Priority 1Both local & cloud

Make “ship or falsify” the default assignment.

Every assignment should name a concrete deliverable before dispatch: a patch, a new decision-changing finding, or a precise blocker. A report-only result is allowed only when it changes the next decision.

  1. Require a novelty statement: the three prior artifacts checked and why this question is still open.
  2. Require a candidate diff and relevant checks if the hypothesis survives.
  3. Require the worker to state at the start whether it is on a delivery path or an evidence-only path.
Priority 1Product gap

Finish the review-to-merge loop.

The controller can prepare and check frozen patches, but it explicitly does not merge or push them. That leaves one of the original Program goals unfinished.

  1. Add an explicit delivery-authority option for a designated integration branch.
  2. Run integration_prepare, integration_check, then merge/cherry-pick the verified commit.
  3. Return the delivered commit and checks, not just the archive commit.
Priority 2Prompt selection

Add prompt-portfolio triage.

The manager workflow tells it to choose a cheap investigation, but there is no automatic scan/ranking of the already-written prompts. This run was steered to a prompt by name.

  1. Scan research/prompts/, the research catalog and recent admissions.
  2. Score each candidate on expected delivered delta, novelty, tool readiness and time to a decision.
  3. Reject prompts whose likely result is “known result, no change.”
Priority 2Reliability

Checkpoint after every collection.

End-of-turn saving is not enough. This run needed a 407-file recovery because the durable copy lagged the experiment.

  1. Push small result files, manifests and failure records immediately.
  2. Compress large journals separately and record omissions.
  3. Make the manager refuse a second collection until the first checkpoint is pushed.
CloudFail fast

Run a real worker-context canary before the main budget.

Manager-side checks were not enough. The worker hit recorder and Node-version failures after dispatch. A short canary would have exposed them cheaply.

  1. Start from env.sh; pin Node 23.11.1.
  2. Run preflight, a socket probe, one tiny collection, a recorder acknowledgement check and one reviewer spawn.
  3. Use viewer: none and record: false for numerical work unless recording is the experiment.
  4. If the canary fails, return the blocker instead of spending the full allocation.
CloudReview

Treat review as a recoverable artifact.

The first reviewer produced a response, but the controller timed out and a second review was run later. Preserve and reuse completed reviewer output whenever provenance still verifies.

  1. Save the reviewer final message before acknowledgement.
  2. On timeout, verify the submission hash and apply or reattach the existing response.
  3. Keep review separate, but do not make it an all-or-nothing live RPC.
Operating modelUse each tool where it wins

Use the direct agent for implementation; use the Program for portfolio and governance.

Until the Program demonstrates the full delivery cycle, the direct Research Agent is the better default for “take this prompt and make it real.” The Program is better suited to comparing prompts, maintaining the evidence graph, and running independent reviews—especially when several investigations or worktrees must be managed.

Cloud
  • Use a 3-hour outer budget with roughly 90–120 minutes for a capable worker, 15–20 for review, and 20–30 for checks/integration.
  • Run one worker at a time on the two-core host; contention already caused cancellations.
  • Keep the parent chat active while the worker and reviewer are live, but do not use it as the execution sandbox.
  • Require remote checkpoints and an explicit blocker report if setup breaks.
Local
  • Use the direct agent for a single implementation prompt; use Program when there is genuine portfolio choice or multi-worktree coordination.
  • Keep goal mode on and allow enough time, but measure delivery rather than elapsed time.
  • Use worktrees plus integration_prepare/integration_check for the merge path.
  • Run an A/B trial before deciding the Program is or is not worth it.

Suggested validation

A three-pair trial will settle more than another anecdote.

Pick three modest, open implementation tasks. Run direct-agent and Program versions from the same base, with the same prompt, model where controllable, permission profile, worker time and delivery authority.

Freeze
Predeclare acceptance.Same task, base revision, prompt, tools, budget and merge target. No posthoc criteria.
Measure
Record delivery, not activity.Integrated commit or verified decision-changing negative finding; human minutes; setup, worker and review minutes; silent failures; required checks.
Decide
Use a simple product gate.Program wins only if it delivers at least two of three changes, exposes every blocker, and cuts your worktree/review/merge time without adding more than one extra human intervention.
Keep
Do not count rereading known evidence.An “existing-evidence review” is useful only when it changes a decision. Otherwise it is a failure of prompt selection.
