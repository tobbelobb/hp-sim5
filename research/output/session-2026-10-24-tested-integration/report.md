# Reviewed findings survive combined patch failures

This engineering task asks whether reviewed scientific findings can remain useful
when candidate patches conflict, become stale, change after review or fail only
in combination. Real Git branches and binary worktrees exercise manager candidate
preparation, finite polled checks, exact revision receipts, exclusive capacity,
stop and restart. Compatible patches pass; two individually passing patches fail
their combined check without changing accepted findings. Version-2 review separates
missing delivery gates from scientific admission while retaining version-1 history.
The corrected affected selection passed 61 tests in 11.47 seconds, with unchanged
passing cases reused from the wider run. Ordinary detached-child detection retains
the lease until observed exit. These are synthetic scientific judgements and
process/Git checks. They establish neither actual physics stability, calibration
accuracy, protected evaluation nor the live manager release.

## Delivered behavior

The [manager integration guide](../../../../research/program-integration.md)
describes the running prepare/check/status/release/recovery operations. Preparation
uses sealed submission IDs and an explicit base. It creates an independent branch
and worktree, freezes the binary patches and combined commit/tree/diff, and keeps
conflicts and failures. Check receipts bind that revision, clean pre/post Git
identities, supplied configuration/input IDs, exact argv, output hashes and evaluator
contract/source hashes. The work never merges or pushes research patches.

Reviewed findings survive engineering outcomes. Reviewer required argv and code
blockers remain binding; the combined physics gate must be the real exact
`npm run test:physics`. The fixtures reject missing gates without invoking a mock
physics command as actual proof. No production dynamics calculations changed.

The store's exclusive lease begins before preparation or check-process startup.
It blocks workers and reviewers, including unopened programs and recovery. Stop
and shutdown observe check cleanup. A runner writes a durable Linux birth receipt
before commands start and has a finite wall deadline. Process-group observation
includes descendants after leader loss. A small subreaper detects ordinary detached
orphans on clean completion and leaves unsupported work charged for explicit recovery.

## Limits and next decision

Development cap was 90 minutes. Numerical budget/use was zero fits, predictions,
replays, physics trials/steps, movements and collections. No new credentials,
HOME/CODEX_HOME changes, network installs, shell fetch/push or live client runs occurred.
Base and supplied upstream main were `03ecf6322797a8eb80162ca59be98b0185906fcf`.

Configuration/input IDs are frozen supplied declarations; actual Git identities,
argv, exit codes and output hashes are observed. Relevant checks must inspect
the actual runtime configuration/inputs before making broader claims.

Cleanup observes the owned Linux process group. Supported checks keep descendants
in that group and finish external services before exit. Clean-completion subreaper
detection does not prove all escaped services stopped after abrupt runner loss.
Other stores, malicious same-UID edits, escaped sessions and external worlds are
outside this cooperative boundary. Unknown startup/cleanup keeps the lease held.

Task 015 is complete. Task 016 remains the real coding-client, worker, production
tool, separate review, graph/replanning and interruption/recovery release gate.
Existing missing native/client prerequisites were not used to block this fixture
task, and these fixtures do not establish manager release readiness.
