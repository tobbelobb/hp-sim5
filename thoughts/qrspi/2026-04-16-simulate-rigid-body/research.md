# Research Findings

## Q1: How does `public/usd_scenes/slideprinter_hexagon.usda` get imported into runtime ECS entities in `hp-sim-3d/app/setupScene.js`, and which authored prims, relationships, and attributes currently define the spool/pinhole assembly, its rigid group, and its constraints?

### Findings
- `slideprinter_hexagon.usda` is one of the selectable scene files in `AVAILABLE_USDAS`; when selected, `addUsdaFromCatalog()` loads it with `UsdOpen(entry.url)`, `registerMachine()` derives a scene root path, and `rebuildScene()` passes that stage into `setupScene()` with `scenePrimPath`, `namespace`, and palette/tint options. `src/js/usd/stage.js:7-45`, `hp-sim-3d/app/hp-sim-3d.js:213-223`, `hp-sim-3d/app/hp-sim-3d.js:1182-1267`, `hp-sim-3d/app/hp-sim-3d.js:1658-1697`
- `UsdOpen()` parses USDA text into a stage-like object with `GetPrimAtPath()` and `Traverse()`. `setupScene()` then resolves the scene root prim with `stage.GetPrimAtPath(scenePrimPath)` and enumerates direct child prims with `getChildren(sceneRoot)`. `src/js/usd/stage.js:7-45`, `src/js/usd/stage.js:68-111`, `hp-sim-3d/app/setupScene.js:75-110`, `hp-sim-3d/app/setupScene.js:319-356`
- `setupScene()` classifies scene children by authored schema/type/relationships: `apiSchemas` containing `CablePathAPI` go to `pathPrims`; prims with `defType === 'CableJoint'` go to `jointPrims`; `defType === 'DistancePhysicsJoint'` go to `distanceJointPrims`; rigid groups are discovered either by `defType === 'RigidGroup'` or by a non-empty `rigidGroup:members` relationship. `src/js/usd/stage.js:68-111`, `hp-sim-3d/app/setupScene.js:332-356`
- Body ECS entities are created from authored `ecs:tags` plus authored transforms/physics attributes. `Spool` tags create spool entities; `Anchor` tags create anchor entities; `Pinhole` or `Attachment` tags create pinhole entities. `hp-sim-3d/app/setupScene.js:358-525`
- In `slideprinter_hexagon.usda`, the spool/pinhole assembly is authored as three spool prims (`SpoolA`, `SpoolB`, `SpoolC`) and six pinhole prims (`PinholeAL`, `PinholeAR`, `PinholeBL`, `PinholeBR`, `PinholeCL`, `PinholeCR`) under `/World/SlideprinterScene`. `public/usd_scenes/slideprinter_hexagon.usda:13-198`
- Each spool prim carries `ecs:tags = ["Spool", "Stepper"]`, `cable:linkable = 1`, `radius`, `xformOp:translate`, `xformOp:orient`, `physics:mass`, `physics:angularVelocity`, `physics:inertiaTensor`, `physics:velocity`, and custom stepper attributes (`stepper:holdingTorque`, `stepper:numPolePairs`, `stepper:dampingCoeff`). `public/usd_scenes/slideprinter_hexagon.usda:14-33`, `public/usd_scenes/slideprinter_hexagon.usda:76-94`, `public/usd_scenes/slideprinter_hexagon.usda:138-156`
- Each pinhole prim carries `ecs:tags = ["Pinhole"]`, `radius`, `xformOp:translate`, `physics:mass`, and `physics:velocity`; in this scene they do not carry `physics:angularVelocity`, `physics:inertiaTensor`, or `cable:linkable`. `public/usd_scenes/slideprinter_hexagon.usda:50-74`, `public/usd_scenes/slideprinter_hexagon.usda:112-136`, `public/usd_scenes/slideprinter_hexagon.usda:174-198`
- Runtime spool entities receive `SpoolTagComponent`, `SpoolStateComponent`, `StepperMotorComponent`, `PositionComponent`, `VelocityComponent`, `RadiusComponent`, `MassComponent`, optional `GravityAffectedComponent`, `RenderableComponent`, `OrientationComponent`, `EncoderComponent`, `AngularVelocityComponent`, scalar `MomentOfInertiaComponent`, `PrevFinalOrientationComponent`, `PrevFinalPosComponent`, optional friction/restitution, and optional `CableLinkComponent`. `hp-sim-3d/app/setupScene.js:378-452`
- Runtime pinhole entities receive `MachineTagComponent`, `PositionComponent`, `VelocityComponent`, optional `RadiusComponent`, `MassComponent`, optional `GravityAffectedComponent`, `RenderableComponent`, optional `OrientationComponent`, optional `PrevFinalOrientationComponent`, optional `AngularVelocityComponent`, optional `MomentOfInertiaComponent`, `PrevFinalPosComponent`, optional friction/restitution, and optional `CableLinkComponent`. In the current pinhole branch they also receive `SpoolTagComponent`. `hp-sim-3d/app/setupScene.js:464-525`
- The rigid group is authored as `def RigidGroup "SpoolTriangle"` with `rel rigidGroup:members = [SpoolA, SpoolB, SpoolC, PinholeAL, PinholeAR, PinholeBL, PinholeBR, PinholeCL, PinholeCR]` and `custom string rigidGroup:renderIndices = "[3,4,5,6,7,8,3]"`. `public/usd_scenes/slideprinter_hexagon.usda:201-216`
- `setupScene()` turns that rigid group prim into a separate ECS entity holding `RigidGroupComponent(memberEntities, 1.0, renderSegments)`, `MachineTagComponent`, and `RenderableComponent('line', ...)`; membership is resolved through `rigidGroup:members` path lookups against the body-entity map. `hp-sim-3d/app/setupScene.js:122-165`, `hp-sim-3d/app/setupScene.js:529-579`
- The assembly’s rigid constraints are also authored as many `DistancePhysicsJoint` prims: spool-to-spool, pinhole-pair, pinhole-to-own-spool, pinhole-to-neighbor-pinhole, and spool-to-nonlocal-pinhole constraints. `public/usd_scenes/slideprinter_hexagon.usda:218-428`
- `setupScene()` creates a runtime `DistanceConstraintComponent` entity for each `DistancePhysicsJoint` whose `physics:minDistance` equals `physics:maxDistance`; the code path that would skip constraints internal to the same rigid group is present but commented out, so those constraints are currently still instantiated. `hp-sim-3d/app/setupScene.js:582-620`
- Cable routing is authored through twelve `CableJoint` prims (`JointAL_0/1` ... `JointCR_0/1`) plus six `CablePathAPI` prims (`CablePathAL` ... `CablePathCR`). The second cable joint in each path carries the local spool attachment offset via `localPos1`; each cable path carries ordered `cablePath:joints`, `cablePath:linkTypes`, `cablePath:clockwise`, `cablePath:stored`, `stiffness`, and `cablePath:halfWidth`. `public/usd_scenes/slideprinter_hexagon.usda:430-615`
- `setupScene()` converts each authored `CableJoint` into its own ECS entity with `CableJointComponent.fromLocal(...)` and each authored cable path into a `CablePathComponent(...)` entity. `hp-sim-3d/app/setupScene.js:623-686`, `src/js/cable_joints_3d/cable_joints_core.js:36-64`, `src/js/cable_joints_3d/cable_joints_core.js:68-113`
- The scene also authors an `Extruder` prim with `machine:centerSources = [SpoolA, SpoolB, SpoolC]` and `machine:rigidGroup = </World/SlideprinterScene/SpoolTriangle>`. `setupScene()` consumes `machine:centerSources` when populating `ExtruderComponent.centerSources`, but no inspected code path in `setupScene.js` reads the authored `machine:rigidGroup` relationship from that extruder prim. `public/usd_scenes/slideprinter_hexagon.usda:617-645`, `hp-sim-3d/app/setupScene.js:363-374`, `hp-sim-3d/app/setupScene.js:688-739`

## Q2: How are rigid-group members represented at runtime today, including which components are attached to the member entities versus the group entity, and how does `RigidGroupSystem` currently compute and enforce group motion?

### Findings
- Runtime rigid-group members remain normal body entities with their own per-entity components; the rigid group itself is a separate ECS entity that only carries grouping metadata/render info. `hp-sim-3d/app/setupScene.js:529-579`
- The group entity created in `setupScene()` gets `RigidGroupComponent`, `MachineTagComponent`, and `RenderableComponent('line', ...)`. It does not receive `PositionComponent`, `VelocityComponent`, `OrientationComponent`, `AngularVelocityComponent`, `MassComponent`, or `MomentOfInertiaComponent`. `hp-sim-3d/app/setupScene.js:561-579`
- `RigidGroupComponent` itself stores `members`, `restLocal`, `stiffness`, `prevAngle`, and optional `renderSegments`; there is no aggregate mass, aggregate inertia tensor, aggregate pose, or aggregate velocity field in the component definition. `src/js/cable_joints/ecs.js:177-189`
- Member entities keep their own body state. For spool members in this loader path that includes linear position/velocity, mass, orientation, angular velocity, scalar inertia, previous-final caches, stepper/spool state, and optional cable-link state. `hp-sim-3d/app/setupScene.js:378-452`
- Member pinhole entities keep their own position/velocity/mass/render data and only get rotational state if the authored prim supplied angular attributes. In `slideprinter_hexagon.usda`, the pinholes do not author angular velocity or inertia, so those particular member entities are created without angular-state components. `public/usd_scenes/slideprinter_hexagon.usda:50-74`, `public/usd_scenes/slideprinter_hexagon.usda:112-136`, `public/usd_scenes/slideprinter_hexagon.usda:174-198`, `hp-sim-3d/app/setupScene.js:464-525`
- `RigidGroupSystem` computes a mass-weighted center of mass from member `PositionComponent` and `MassComponent`; members with non-positive mass are ignored in that COM sum. `src/js/cable_joints_3d/commonSystems.js:349-365`
- On first update, `RigidGroupSystem` initializes `group.restLocal` from the current member positions relative to that COM, chooses a reference triangle from those local offsets, and precomputes `group.restPairs` as all pairwise member rest distances. `src/js/cable_joints_3d/commonSystems.js:381-397`
- Positional rigidity is enforced by iterating every stored rest pair and directly correcting the two member `PositionComponent.pos` vectors using inverse masses and the pair’s rest length. This is a pairwise member correction, not a move of the group entity. `src/js/cable_joints_3d/commonSystems.js:399-428`
- After those pair corrections, `RigidGroupSystem` recomputes COM and estimates a group rotation from current member positions versus `group.restLocal` using `estimateGroupRotation()`, which builds orthonormal frames from a reference triangle and converts the resulting rotation matrix into a quaternion. `src/js/cable_joints_3d/commonSystems.js:157-193`, `src/js/cable_joints_3d/commonSystems.js:430-450`
- The computed delta rotation is applied to each member individually via `applyOrientationDelta(world, entityId, deltaRotation)`. That helper mutates the member’s `OrientationComponent.quaternion` and, when present, rotates the member’s `SpoolStateComponent` reference orientation. `src/js/cable_joints_3d/commonSystems.js:72-82`, `src/js/cable_joints_3d/commonSystems.js:436-447`
- The group entity’s own transform is not advanced by `RigidGroupSystem`; the system mutates member entities in place and only stores `group.prevRotation` and `group.prevAngle` back on the `RigidGroupComponent`. `src/js/cable_joints_3d/commonSystems.js:436-450`

## Q3: How does `PBDCableConstraintSolver` trace cable-path data into attachment points, gradients, mass/inertia terms, and position/orientation corrections, and at which points does it operate on individual entities rather than any aggregate body state?

### Findings
- `CablePathComponent` stores the ordered path-level data that the solver consumes: `jointEntities`, `linkTypes`, `cw`, `spring_constant`, `compliance`, `stored`, and `cableHalfWidth`. Compliance is derived as `1.0 / spring_constant`. `src/js/cable_joints_3d/cable_joints_core.js:68-113`
- Before the cable solver runs, `CableAttachmentUpdateSystem` updates joint attachment points and joint rest lengths from the current path topology/state by calling `_updateAttachmentPoints()`, then `_mergeJoints()`, `_splitJoints()`, and `_updateHybridLinkStates()`. `hp-sim-3d/app/setupScene.js:788-799`, `src/js/cable_joints_3d/cable_joints_core.js:1311-1335`
- `_updateAttachmentPoints()` traces each path through its `CableJointComponent`s and `linkTypes`, reads member positions/orientations, previous attachment-time caches, effective rolling radii, and hybrid/friction state, then writes updated `joint.attachmentPointA_world`, `joint.attachmentPointB_world`, `path.stored[...]`, and `joint.restLength`. `src/js/cable_joints_3d/cable_joints_core.js:531-637`, `src/js/cable_joints_3d/cable_joints_core.js:643-1075`
- `calculateAttachmentPoints()` is the geometric bridge from path state into actual world attachment points. It reads `joint.entityA/entityB`, the path’s endpoint/middle `linkTypes`, current and previous entity transforms, plane normals, and rolling directions, then chooses tangency computations based on whether each side is attachment, pinhole, rolling, or hybrid. `src/js/cable_joints_3d/cable_joints_core.js:531-637`
- `PBDCableConstraintSolver` queries `CablePathComponent` entities, reads `dt` from the world resource, and uses a hardcoded `ITERATIONS = 2`. `src/js/cable_joints_3d/cable_joints_core.js:1338-1346`
- At the beginning of a solve step, it snapshots each joint’s current attachment points into per-joint local coordinates with a `jointLocals` map. `computeLocal()` expresses `joint.attachmentPointA_world` and `joint.attachmentPointB_world` in the local frame of `joint.entityA` and `joint.entityB` by subtracting body position and, if present, applying the inverse body orientation. `src/js/cable_joints_3d/cable_joints_core.js:1346-1360`, `src/js/cable_joints_3d/cable_joints_core.js:1453-1461`
- During each forward/backward iteration, the solver reconstructs the current world attachment points from those stored locals using `_computeWorldAttachment(world, entityId, localPoint)`, which re-applies the current `PositionComponent` and current `OrientationComponent` for that entity. `src/js/cable_joints_3d/cable_joints_core.js:208-226`, `src/js/cable_joints_3d/cable_joints_core.js:1477-1484`
- Constraint gradients are built per joint and per endpoint: `gradPosA = dir`, `gradPosB = -dir`, with angular gradients `gradAngA = rA x gradPosA` and `gradAngB = rB x gradPosB`, where `rA` and `rB` are attachment offsets from each body’s current center position. `src/js/cable_joints_3d/cable_joints_core.js:1397-1404`, `src/js/cable_joints_3d/cable_joints_core.js:1487-1497`
- Mass and rotational terms are read from each endpoint entity individually: inverse linear mass comes from `MassComponent.mass`, and inverse rotational inertia comes from the scalar `MomentOfInertiaComponent.invInertia`. There is no query for `RigidGroupComponent` and no aggregate body mass/inertia lookup. `src/js/cable_joints_3d/cable_joints_core.js:1374-1386`
- The denominator is assembled from per-entity translational and angular terms plus path compliance (`compliance / (dt * dt)`). `src/js/cable_joints_3d/cable_joints_core.js:1397-1409`
- Positional corrections are applied directly to `entityA` and `entityB` by mutating their `PositionComponent.pos`. Rotational corrections are applied directly to those same entities by mutating `OrientationComponent.quaternion` through an axis-angle delta quaternion. `src/js/cable_joints_3d/cable_joints_core.js:1410-1438`
- The solver only acts on extension (`constraintError = currentSegmentLength - joint.restLength`; it returns early unless `constraintError > EPSILON`). `src/js/cable_joints_3d/cable_joints_core.js:1487-1497`
- Every stage of the cable solve is keyed to individual endpoint entities (`joint.entityA`, `joint.entityB`) and individual joint entities in a path. No inspected branch of `PBDCableConstraintSolver` operates on a rigid-group aggregate state or a group entity. `src/js/cable_joints_3d/cable_joints_core.js:1453-1499`

## Q4: How do `XPBDDistanceConstraintSystem`, `RigidGroupSystem`, and `PBDCableConstraintSolver` interact within the registered system order, and what correction ordering, iteration structure, or state handoff could explain amplified impulses or energy injection across grouped members?

### Findings
- The registered order in `setupScene()` is: cache previous state (`PrevFinalPosSystem`, `PrevFinalOrientationSystem`), predict motion (`GravitySystem`, `MovementSystem`, `AngularMovementSystem`), update cable attachments/path state (`CableAttachmentUpdateSystem`, `CableAttachmentCacheSystem`, `CableSlackSystem`), solve cable constraints (`PBDCableConstraintSolver`, `PBDResolveCableOverCorrections`), enforce rigid/group and distance constraints (`RigidGroupSystem`, `XPBDDistanceConstraintSystem`, `SpoolAxisConstraintSystem`), then reconstruct velocities (`PBDVelocityUpdateSystem`, `PBDAngularVelocityUpdateSystem`). `hp-sim-3d/app/setupScene.js:774-817`
- `PBDCableConstraintSolver` runs before `RigidGroupSystem` and `XPBDDistanceConstraintSystem`, so cable corrections are applied to member entities first, and then later systems apply additional corrections to those same member entities in the same frame. `hp-sim-3d/app/setupScene.js:788-808`, `src/js/cable_joints_3d/cable_joints_core.js:1338-1499`, `src/js/cable_joints_3d/commonSystems.js:231-287`, `src/js/cable_joints_3d/commonSystems.js:346-453`
- `PBDCableConstraintSolver` has its own internal two-iteration forward/backward sweep over paths and joints. `RigidGroupSystem` then performs its own all-pairs member correction pass plus a rotation pass. `XPBDDistanceConstraintSystem` then performs another pass over all distance-constraint entities. `src/js/cable_joints_3d/cable_joints_core.js:1453-1499`, `src/js/cable_joints_3d/commonSystems.js:399-450`, `src/js/cable_joints_3d/commonSystems.js:231-287`
- The authored `DistancePhysicsJoint` constraints for the spool/pinhole assembly are still instantiated even when both endpoints belong to the same rigid group, because the same-group skip is commented out in `setupScene()`. That means rigid-group members can be corrected by both `RigidGroupSystem` and separate `DistanceConstraintComponent` entities in the same update sequence. `public/usd_scenes/slideprinter_hexagon.usda:201-428`, `hp-sim-3d/app/setupScene.js:582-620`
- `RigidGroupSystem` itself does not consume the distance-constraint lambda state or cable-solver internals; it reads current member positions, pushes pairwise rest-distance corrections, and then rotates members. `XPBDDistanceConstraintSystem` similarly reads the current member positions after prior corrections and applies its own positional solve with persistent `constraint.lambda`. `src/js/cable_joints_3d/commonSystems.js:231-287`, `src/js/cable_joints_3d/commonSystems.js:346-453`
- Velocity reconstruction is deferred until after all of those positional/orientational corrections have been accumulated. `PBDVelocityUpdateSystem` and `PBDAngularVelocityUpdateSystem` then derive velocities from the difference between the start-of-frame caches and the final corrected member states. `hp-sim-3d/app/setupScene.js:808-813`, `src/js/cable_joints_3d/commonSystems.js:480-566`
- In the current code, the state handoff between these systems is the member entities’ live `PositionComponent` and `OrientationComponent` data. No inspected handoff uses a rigid-group aggregate pose or aggregate momentum state. `src/js/cable_joints_3d/cable_joints_core.js:1410-1438`, `src/js/cable_joints_3d/commonSystems.js:399-450`, `src/js/cable_joints_3d/commonSystems.js:504-566`

## Q5: How are linear and angular state cached and reconstructed across a frame—especially via `PrevFinalPos*`, `PrevFinalOrientation*`, `PBDVelocityUpdateSystem`, and `PBDAngularVelocityUpdateSystem`—and what assumptions do those systems make about bodies being individual entities rather than compound ones?

### Findings
- At the start of each simulation frame, `PrevFinalPosSystem` copies each entity’s current `PositionComponent.pos` into `PrevFinalPosComponent.pos`, and `PrevFinalOrientationSystem` copies each entity’s current `OrientationComponent.quaternion` into `PrevFinalOrientationComponent.quaternion`. `hp-sim-3d/app/setupScene.js:774-780`, `src/js/cable_joints_3d/commonSystems.js:301-310`, `src/js/cable_joints_3d/commonSystems.js:480-489`
- These previous-final caches are attached to individual body entities, not to group entities. In `setupScene()`, spools always get both previous-final caches; pinholes only get `PrevFinalOrientationComponent` if they also authored angular velocity/orientation state. `hp-sim-3d/app/setupScene.js:420-444`, `hp-sim-3d/app/setupScene.js:487-519`
- Predicted motion then advances per-entity state through `GravitySystem`, `MovementSystem`, and `AngularMovementSystem`, which mutate `VelocityComponent`, `PositionComponent`, and `OrientationComponent` on the same individual entities. `hp-sim-3d/app/setupScene.js:784-787`, `src/js/cable_joints_3d/commonSystems.js:215-228`, `src/js/cable_joints_3d/commonSystems.js:289-299`, `src/js/cable_joints_3d/commonSystems.js:455-478`
- After all positional solvers, `PBDVelocityUpdateSystem` reconstructs linear velocity as `(currentPos - prevFinalPos) / dt` for each entity that has `PositionComponent`, `VelocityComponent`, `PrevFinalPosComponent`, and `MassComponent`, skipping grabbed entities and any entity with `mass <= 0`. `src/js/cable_joints_3d/commonSystems.js:491-511`
- `PBDAngularVelocityUpdateSystem` reconstructs angular velocity from the quaternion delta `qCurr * inverse(qPrev)` for each entity that has `OrientationComponent`, `AngularVelocityComponent`, `PrevFinalOrientationComponent`, and `MomentOfInertiaComponent`, skipping grabbed entities and any entity with `invInertia <= 0`. `src/js/cable_joints_3d/commonSystems.js:513-566`
- The angular reconstruction path depends on per-entity previous/current quaternions and per-entity scalar inertia gating. It does not read `RigidGroupComponent`, `group.prevRotation`, or any compound-body state. `src/js/cable_joints_3d/commonSystems.js:513-566`
- Because `RigidGroupSystem` mutates member positions/orientations directly, those group corrections are folded into each member’s reconstructed velocity/omega rather than being reconstructed once at a group-body level. `src/js/cable_joints_3d/commonSystems.js:436-450`, `src/js/cable_joints_3d/commonSystems.js:491-566`
- The group entity created in `setupScene()` does not carry previous-final caches or current pose/velocity components, so the cache/reconstruction systems have nothing group-level to read back. `hp-sim-3d/app/setupScene.js:561-579`
- In `slideprinter_hexagon.usda`, spool members author angular data and therefore receive angular caches; the pinhole members in that scene do not author angular data and therefore are not present in the angular-cache/angular-velocity reconstruction queries. `public/usd_scenes/slideprinter_hexagon.usda:14-33`, `public/usd_scenes/slideprinter_hexagon.usda:50-74`, `public/usd_scenes/slideprinter_hexagon.usda:76-94`, `public/usd_scenes/slideprinter_hexagon.usda:112-136`, `public/usd_scenes/slideprinter_hexagon.usda:138-156`, `public/usd_scenes/slideprinter_hexagon.usda:174-198`, `hp-sim-3d/app/setupScene.js:420-444`, `hp-sim-3d/app/setupScene.js:487-519`

## Q6: What inertia and mass abstractions exist in the 3D ECS today, including the use of scalar `MomentOfInertiaComponent`, effective-axis inertia in scene setup, and any comments or code paths that discuss limits of the current model for general 3D rigid bodies or rigid groups?

### Findings
- The 3D ECS re-exports `MassComponent` and `MomentOfInertiaComponent` from the 2D ECS implementation rather than defining a new tensor-valued inertia component. `src/js/cable_joints_3d/ecs.js:5-29`
- The 3D ECS file explicitly documents that `MomentOfInertiaComponent` is “still a scalar inertia from the 2D implementation,” and that in 3D it is currently interpreted as an effective scalar inertia about the constraint axis (or isotropic inertia for spheres). The same comment states that a full `3x3` tensor would be needed for general 3D rigid bodies or rigid groups with anisotropic inertia. `src/js/cable_joints_3d/ecs.js:9-18`
- The underlying `MomentOfInertiaComponent` stores only `inertia` and `invInertia`; it has no tensor fields. `src/js/cable_joints/ecs.js:142-148`
- `setupScene()` computes spool inertia by projecting the authored `physics:inertiaTensor` onto a chosen local axis with `effectiveInertiaAboutAxis(inertiaTensor, axisLocal)`, then stores the resulting scalar in `MomentOfInertiaComponent`. `hp-sim-3d/app/setupScene.js:213-236`, `hp-sim-3d/app/setupScene.js:392-444`
- The axis used for spool inertia is resolved by `readSpoolAxisLocal()`, which checks `spool:axisLocal`, then `machine:axisLocal`, then `physics:rotationAxis`, and otherwise falls back to the default plane normal. `hp-sim-3d/app/setupScene.js:205-211`
- For pinhole/attachment entities, when an authored `physics:inertiaTensor` exists, `setupScene()` also projects it to a scalar with `effectiveInertiaAboutAxis(...)`, using the default plane normal rather than a spool axis. `hp-sim-3d/app/setupScene.js:487-519`
- In `slideprinter_hexagon.usda`, only the spool prims author `physics:inertiaTensor`; the pinholes only author mass and linear velocity. That means the runtime scalar inertia abstraction is populated for spools in this scene, but not for its pinholes. `public/usd_scenes/slideprinter_hexagon.usda:14-33`, `public/usd_scenes/slideprinter_hexagon.usda:50-74`, `public/usd_scenes/slideprinter_hexagon.usda:76-94`, `public/usd_scenes/slideprinter_hexagon.usda:112-136`, `public/usd_scenes/slideprinter_hexagon.usda:138-156`, `public/usd_scenes/slideprinter_hexagon.usda:174-198`
- `PBDCableConstraintSolver` uses the scalar `invInertia` directly in its angular denominator and angular correction steps; no tensor rotation into world space is performed. `src/js/cable_joints_3d/cable_joints_core.js:1374-1438`
- `RigidGroupSystem` uses member `MassComponent` values for COM weighting and pair corrections, but it does not assemble a group-level effective mass or inertia abstraction. `src/js/cable_joints_3d/commonSystems.js:349-365`, `src/js/cable_joints_3d/commonSystems.js:399-450`
- `PBDAngularVelocityUpdateSystem` also treats rotational state as per-entity scalar-inertia state by gating on `MomentOfInertiaComponent.invInertia` before reconstructing angular velocity. `src/js/cable_joints_3d/commonSystems.js:513-566`

## Cross-Cutting Observations

- The runtime model is entity-centric: authored spool, pinhole, anchor, cable-joint, cable-path, distance-joint, and rigid-group prims become separate ECS entities or metadata over separate ECS entities rather than a single aggregate “compound body” object. `hp-sim-3d/app/setupScene.js:332-739`
- In the inspected 3D path, rigid groups are overlays on member entities, not replacements for them: cable constraints, rigid-group corrections, distance constraints, velocity reconstruction, and encoder/orientation updates all continue to read and write the member entities directly. `hp-sim-3d/app/setupScene.js:774-817`, `src/js/cable_joints_3d/cable_joints_core.js:1338-1499`, `src/js/cable_joints_3d/commonSystems.js:231-287`, `src/js/cable_joints_3d/commonSystems.js:346-566`
